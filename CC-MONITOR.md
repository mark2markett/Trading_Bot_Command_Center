# Native ongoing health observations

Install with INSTALL-CC-MONITOR.ps1. It adds only CC health monitor; existing server, bot, backup and opening verification settings stay intact. Files are stored under ignored var/monitor, with daily JSONL under var/logs and an atomic latest.json. Each observation reads /api/health and /api/readiness, a read-only SQLite snapshot, and the platform public health endpoint. No credential files are read by the monitor. The separate one-time collector uses the existing authorized authenticated scanner evidence path.

Checks include riskd freshness (90 seconds), current shared paper valuation, the exact five-paper-bot registration, fleet entry controls, four intraday heartbeats (10-minute grace), stored bot health and today's SIP universe decision. A valid empty universe is accepted. After 09:40, absent universe or SCANNER_UNAVAILABLE is reported as failure; an older day's successful scan cannot pass. Outside the trading window, continuous intraday heartbeats and today's opening universe are not required. The monitor does not test live vendor quotes, certify all function paths or establish scanner timeliness retrospectively from a UNIVERSE row alone. Preserve the existing morning live-readiness check.

The daily SPY reconcile and decide commands are checked independently after their scheduled time plus ten minutes; they do not need continuous heartbeats. The calendar's early-close decide time is respected. Ten minutes after the close, any remaining intraday position is flagged; legitimate overnight daily-SPY positions are excluded. These checks report failures and never place flatten orders.

The task observes every five minutes, skips overlapping executions and has a three-minute limit. The server's existing Windows account/logon behavior is inherited; interactive accounts still require a signed-in user. The Windows wrapper may start only an enabled CC server task that is stopped and belongs to this repository, at most once per thirty minutes. It never force-stops a running server, starts/restarts bots, clears risk controls, changes balances or repeats late opening selection. A hung server, stale heartbeat, failed scan or valuation failure is recorded for investigation.

An initial review ZIP is collected once and printed on installation. Recurring observations do not create repeated full database backups. These local reports are not automatically delivered to this cloud chat, and this chat is not a continuously running supervisor after a turn ends. Share the ZIP or current report to enable diagnosis of native incidents here. Existing riskd dashboard alerts continue every 15 seconds; external human notification channels require separately configured routing.

The one-time collector reads enrichment job telemetry, the latest enrichment timestamp and eligibility existence checks using existing shared Supabase credentials in memory, over HTTPS without redirects. It exports only timestamps, known status values, numeric counts and existence flags. Credentials and raw error/detail strings are excluded. HTTP failures stay explicit rather than becoming empty-success evidence. No platform job is triggered and no database changes are made.

For SIP incidents the collector also saves today's cc-sip-scanner preparation/publication telemetry in platform-sip.json. It retains known producer failure codes, phases and counts while excluding arbitrary error strings. Use those records with ledger SCANNER decisions to explain a missed 09:40 deadline; the deadline heartbeat alone does not identify the upstream cause. An unavailable telemetry read is not proof that the scheduled job never ran. Collection does not restart the bot or attempt a late publication.
